## 1. ROS 快照

- [根目录](http://snapshots.ros.org/)有 Humble、Jazzy；`/rolling/` 实测 HTTP 404。
  这是当前可用性观察，不是永远不支持 Rolling 的承诺。
- [Jazzy 目录](http://snapshots.ros.org/jazzy/)有 18 个日期，从 `2024-05-23`
  到 `2026-09-11`，相邻日期间隔 17–100 天。不能假定每日、固定月度或任意日期存在。
- 实际布局为 `http://snapshots.ros.org/<distro>/<date>/ubuntu/dists/<suite>/…`。
  `jazzy/2026-09-11/ubuntu/dists/noble/Release` 的内容为：

```text
Origin: ROS
Label: jazzy/2026-09-11/ubuntu noble
Suite: noble
Codename: noble
Date: Fri, 11 Sep 2026 18:21:46 UTC
Architectures: amd64 arm64 armhf i386
Components: main
Description: Generated by aptly
```

该目录下 `main/binary-amd64/Packages.gz` 和 `main/binary-arm64/Packages.gz`
均下载成功，缓存文件的字节数和 SHA256 均与 Release 对应条目一致；
两份索引均包含对应架构的 `ros-jazzy-ros-workspace`。这仅证明缓存内容与 Release
一致，不能代替 Release 签名认证，也不代表所有 ROS 包在所有架构上都有构建。

```bash
curl -fsSL http://snapshots.ros.org/jazzy/
curl -fsSL http://snapshots.ros.org/jazzy/2026-09-11/ubuntu/dists/noble/Release
curl -fsSL http://snapshots.ros.org/jazzy/2026-09-11/ubuntu/dists/noble/main/binary-arm64/Packages.gz -o Packages.gz
gzip -dc Packages.gz | head
```

HTTPS 实测失败：`curl: (60) ... certificate subject name ...`。
HTTP 的 Release.gpg 签名使用密钥 `4B63CF8FDE49746E98FA01DDAD19BAB3CBF125EA`；
用 `ros/rosdistro/master/ros.key` 执行 `gpgv` 返回 `No public key`。
另对缓存的 `ros.asc` 转换 keyring 后复验，仍返回相同错误（退出码 2）；
该密钥指纹为 `C1CF6E31E6BADE8868B172B4F42ED6FBAB17C654`，与签名密钥不同。
因此上述索引只能作为格式/可达性证据，**尚未完成可信安装源认证**。
后续需从可信官方渠道定位快照签名密钥并验证；不得使用 `trusted=yes` 或关闭签名检查。

P2 必须先发现真实日期并验证 suite、架构、签名和目标版本，再写入 lock；
不能直接把请求日期拼入 URL。Rolling 快照不可用时按 spec §3.2 告警降级。

## 2. Ubuntu 22.04 快照

[官方服务说明](https://snapshot.ubuntu.com/)明确支持更新后的 Ubuntu 22.04
（APT **2.4.11** 起）及 20.04（APT 2.0.10 起）。原 spec 的
“必须 2.7.14+，22.04 只能直写 URL”前提不成立。
官方说明快照从 2023-03-01 起提供，目标保留至少两年；这不是无限期存档保证。

本机 APT 2.4.14 实测两种配置，均保留 Ubuntu archive keyring 签名验证：

```text
# ubuntu.list：使用原生参数 --snapshot 20250901T000000Z
deb [arch=amd64 signed-by=/usr/share/keyrings/ubuntu-archive-keyring.gpg snapshot=yes] http://archive.ubuntu.com/ubuntu jammy main

# ubuntu-direct.list：不需要 --snapshot
deb [arch=amd64 signed-by=/usr/share/keyrings/ubuntu-archive-keyring.gpg] https://snapshot.ubuntu.com/ubuntu/20250901T000000Z/ jammy main
```

可在新建临时目录中创建上述文件并运行（`probe` 指向该目录）：

```bash
mkdir -p "$probe/lists/partial" "$probe/cache/archives/partial"
apt-get -o Dir::Etc::sourcelist="$probe/ubuntu.list" \
  -o Dir::Etc::sourceparts=- -o Dir::State::lists="$probe/lists" \
  -o Dir::Cache="$probe/cache" --snapshot 20250901T000000Z update
```

原生模式成功获取实时索引和指定快照索引；因此不能仅凭 `update` 输出证明
后续安装也被锁定，查询/安装仍须传递快照参数或固定源的 snapshot ID。
直接 URL 模式使用另一独立 lists 目录执行 `update` 成功，`apt-cache policy hello`
仅显示快照候选 `2.10-2ubuntu4`。随后 `apt-get download hello=2.10-2ubuntu4`
成功，`dpkg-deb -f` 确认 `hello / 2.10-2ubuntu4 / amd64`，未安装该包。

本次测试覆盖 jammy/main/amd64；正式实现还须覆盖 updates/security、所需 components
与 arm64，不能将此冒烟测试解释成完整依赖闭包验证。

## 4. RoboStack rosdep 源与 skip_keys

实际源链：

- [conda-forge rosdep 配方](https://github.com/conda-forge/rosdep-feedstock/blob/main/recipe/meta.yaml)
  为 0.26.0、build 1，应用 `add-robostack.patch`、`810.patch`、`no-sudo.patch`。
- [add-robostack.patch](https://github.com/conda-forge/rosdep-feedstock/blob/main/recipe/add-robostack.patch)
  把默认源列表改为
  `https://raw.githubusercontent.com/RoboStack/rosdistro/master/rosdep/sources.list.d/20-default.list`。
- 该列表优先加载 `https://raw.githubusercontent.com/RoboStack/ros-noetic/master/conda.yaml`，
  再加载标准 base/python/ruby YAML。路径中的 noetic 不能被误解为只可解析 Noetic 系统依赖。
- `ROSDEP_SOURCE_PATH` 可隔离 sources 目录，`ROS_HOME` 可隔离缓存；指定
  `--os=conda:linux`。不要把 native 和 Pixi 的全局源列表相互覆盖。
- `ros-humble/main/robostack.yaml` 是 vinca 构建映射，使用 `robostack:` 键，
  不是上述 `conda:` rosdep 源的直接替代品。

实测使用上游 rosdep master 源码（报告版本 0.27.0），从下载的三份 YAML
生成独立缓存，执行 `update --rosdistro humble` 成功。相同键解析结果：

| rosdep 键 | `--os=ubuntu:jammy` | `--os=conda:linux` |
|---|---|---|
| boost | libboost-all-dev | libboost-devel libboost-python-devel |
| cmake | cmake | cmake |
| python3-numpy | python3-numpy | numpy |
| libopencv-dev | libopencv-dev | py-opencv libopencv libopengl-devel libgl-devel |
| rclcpp | ros-humble-rclcpp | **No definition of [rclcpp] for OS [conda]** |

上游 conda 后端仅支持映射，检测/安装抛出 `NotImplementedError`。
conda-forge 的 `810.patch` 另外为 ROS 发行包生成 conda 映射，包含调用
conda/mamba/micromamba 的安装逻辑；**它与未经补丁的上游不是等价环境**。
本次已审阅补丁，但尚未运行这个 conda-forge 构建，因此不把 `rclcpp` 的 conda
解析标为通过。缓存的 conda-forge 元数据已定位待验证构建：
`noarch/rosdep-0.26.0-pyhd8ed1ab_1.conda`，SHA256 为
`73eebdcdebc4f78053dcfcd7366a3a07ad7e6c259125c1f22e411816a1fff89f`；
包文件尚未下载。应在独立环境中运行该构建，以相同源解析 `rclcpp`，
确认输出 `ros-humble-rclcpp` 并复核上表系统键；不能用手工改造 master 替代发行构建验证。
P3 需要探测并固定具备所需映射能力的 rosdep 版本/构建，安装交给 Pixi。

对包含上表前四个依赖的 `package.xml` 执行：

```bash
python3 -m rosdep2 keys --from-paths "$probe/ws/src" --ignore-src \
  --rosdistro humble --skip-keys libopencv-dev
```

输出仍包含 `libopencv-dev`，与源码仅对 install/check 应用 skip_keys 一致。
因此清单可共用**原始 rosdep 键**的 skip_keys，但 Pixi 的 keys/resolve 流程须自行
在解析前过滤；不能拿 apt 包名过滤 conda 解析结果。包名相同不代表所有键跨提供者存在。
