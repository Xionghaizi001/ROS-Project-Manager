## 1. ROS 快照

- [根目录](http://snapshots.ros.org/)有 Humble、Jazzy、Lyrical 等；`/rolling/` 实测 HTTP 404。
  这是当前可用性观察，不是永远不支持 Rolling 的承诺。
- [Jazzy 目录](http://snapshots.ros.org/jazzy/)有 18 个日期，从 `2024-05-23`
  到 `2026-09-11`，相邻日期间隔 17–100 天。不能假定每日、固定月度或任意日期存在。
- 实际布局为 `http://snapshots.ros.org/<distro>/<date>/ubuntu/dists/<suite>/…`。
  `jazzy/2026-09-11/ubuntu/dists/noble/Release` 的内容为：

```text
Origin: ROS
Label: jazzy/2026-09-11/ubuntu noble
Suite: noble
Codename: noble
Date: Fri, 11 Sep 2026 18:21:46 UTC
Architectures: amd64 arm64 armhf i386
Components: main
Description: Generated by aptly
```

该目录下 `main/binary-amd64/Packages.gz` 和 `main/binary-arm64/Packages.gz`
均下载成功，缓存文件的字节数和 SHA256 均与 Release 对应条目一致；
两份索引均包含对应架构的 `ros-jazzy-ros-workspace`。这不代表所有 ROS 包在所有架构上都有构建。

```bash
curl -fsSL http://snapshots.ros.org/jazzy/
curl -fsSL http://snapshots.ros.org/jazzy/2026-09-11/ubuntu/dists/noble/Release
curl -fsSL http://snapshots.ros.org/jazzy/2026-09-11/ubuntu/dists/noble/main/binary-arm64/Packages.gz -o Packages.gz
gzip -dc Packages.gz | head
```

HTTPS 实测失败：`curl: (60) ... certificate subject name ...`，只能走 HTTP，因此签名验证是唯一的完整性保障。

### 1.1 签名密钥来源与验证（2026-09-25 完成）

`Release.gpg` 与 `InRelease` 的签名密钥均为 `4B63CF8FDE49746E98FA01DDAD19BAB3CBF125EA`。
它**不是** `packages.ros.org` 的密钥（`ros/rosdistro/master/ros.key`，指纹
`C1CF6E31E6BADE8868B172B4F42ED6FBAB17C654`）；两把密钥各签各的仓库，用 `ros.key`
验证快照 Release 必然报 `No public key`。这不是异常，是设计如此。

来源核验（三条独立线索指向同一指纹）：

1. 官方 wiki 页 [SnapshotRepository](https://wiki.ros.org/SnapshotRepository)
   "Usage" 第 2 步给出的就是这把密钥，并指示从 `keyserver.ubuntu.com` 获取。
2. OSRF 官方镜像 `osrf/docker_images` 的快照类 Dockerfile（例如
   `ros/foxy/ubuntu/focal/ros-core/Dockerfile`）用同一指纹从 `keyserver.ubuntu.com`
   拉取并导出为 `/usr/share/keyrings/ros2-snapshots-archive-keyring.gpg`，
   再以 `signed-by=` 引用。
3. Discourse 线程 [Again... Snapshot repo GPG key expired](https://discourse.ros.org/t/again-snapshot-repo-gpg-key-expired/34733)
   与 [osrf/docker_images#697](https://github.com/osrf/docker_images/issues/697)：
   ROS 基础设施维护者 (j-rivero) 确认这是快照仓库的签名密钥，2023-11 曾过期并被延长，
   并指出可在 Ubuntu keyserver 上核对。

本机实测：

```bash
gpg --no-default-keyring --keyring ./snap.gpg \
    --keyserver hkps://keyserver.ubuntu.com \
    --recv-keys 4B63CF8FDE49746E98FA01DDAD19BAB3CBF125EA
gpgv --keyring ./snap.gpg Release.gpg Release   # exit 0
gpgv --keyring ./snap.gpg InRelease             # exit 0
```

结果：`Good signature from "ROS Spanshot builder <rosbuild@ros.org>"`（uid 拼写为上游原样，
另有 `ROS Snapshot builder` uid）。密钥为 rsa3072，创建于 2018-11-19，**有效期至 2027-06-01**；
`keys.openpgp.org` 上没有这把密钥。`packages.ros.org` 的 Release 用 `ros.key` 验证同样通过，
证明本机 gpgv 流程本身没有问题。

留证：

```text
03f52f8b2f9d9e46d8233f6d1dedf822177e67b12933cba8af0026198c97cf57  InRelease
126d9a10b23aa99cc6f49abd73fbee2f9e687dbb8f4d578d24c08b064e5729a5  Release
3e30925b14dd5378aae5898f73a11e7f58f2bf7834a787ba07199d40995a6c9f  Release.gpg
9b3c9c698b9a5dcfc3ab26692bdfd349b50994c448ef10347568e6f5eaa3c9f2  snap-key.asc（keyserver 导出的 ASCII 公钥）
```

对 P2 的约束：

- 快照源必须写成 `deb [signed-by=<rospm 管理的 keyring>] http://snapshots.ros.org/...`，
  keyring 由 rospm 从 keyserver 获取后按指纹校验，或随 rospm 内置并按指纹校验；
  禁止 `trusted=yes`、禁止关闭签名检查。
- 密钥曾于 2023-11-19 和 2025-06-01 两次过期，当前有效期到 2027-06-01。`apply --locked`
  遇到 `EXPKEYSIG` 时应提示重新从 keyserver 刷新密钥，而不是降级为不验证。
- 快照仓库没有发布 `ros.key` 之类的密钥文件（根目录及各日期目录下探测均 404），
  keyserver 是官方指定的分发渠道。
- 仍须先发现真实日期并验证 suite、架构、签名和目标版本，再写入 lock；
  不能直接把请求日期拼入 URL。Rolling 快照不可用时按 spec §3.2 告警降级。

## 2. Ubuntu 22.04 快照

[官方服务说明](https://snapshot.ubuntu.com/)明确支持更新后的 Ubuntu 22.04
（APT **2.4.11** 起）及 20.04（APT 2.0.10 起）。原 spec 的
"必须 2.7.14+，22.04 只能直写 URL"前提不成立。
官方说明快照从 2023-03-01 起提供，目标保留至少两年；这不是无限期存档保证。

本机 APT 2.4.14 实测两种配置，均保留 Ubuntu archive keyring 签名验证：

```text
# ubuntu.list：使用原生参数 --snapshot 20250901T000000Z
deb [arch=amd64 signed-by=/usr/share/keyrings/ubuntu-archive-keyring.gpg snapshot=yes] http://archive.ubuntu.com/ubuntu jammy main

# ubuntu-direct.list：不需要 --snapshot
deb [arch=amd64 signed-by=/usr/share/keyrings/ubuntu-archive-keyring.gpg] https://snapshot.ubuntu.com/ubuntu/20250901T000000Z/ jammy main
```

可在新建临时目录中创建上述文件并运行（`probe` 指向该目录）：

```bash
mkdir -p "$probe/lists/partial" "$probe/cache/archives/partial"
apt-get -o Dir::Etc::sourcelist="$probe/ubuntu.list" \
  -o Dir::Etc::sourceparts=- -o Dir::State::lists="$probe/lists" \
  -o Dir::Cache="$probe/cache" --snapshot 20250901T000000Z update
```

原生模式成功获取实时索引和指定快照索引；因此不能仅凭 `update` 输出证明
后续安装也被锁定，查询/安装仍须传递快照参数或固定源的 snapshot ID。
直接 URL 模式使用另一独立 lists 目录执行 `update` 成功，`apt-cache policy hello`
仅显示快照候选 `2.10-2ubuntu4`。随后 `apt-get download hello=2.10-2ubuntu4`
成功，`dpkg-deb -f` 确认 `hello / 2.10-2ubuntu4 / amd64`，未安装该包。

本次测试覆盖 jammy/main/amd64；正式实现还须覆盖 updates/security、所需 components
与 arm64，不能将此冒烟测试解释成完整依赖闭包验证。

## 3. pixi-pack / RoboStack / aarch64（2026-09-25 完成真实打包）

实际上游是 [Quantco/pixi-pack](https://github.com/Quantco/pixi-pack)。
[README](https://github.com/Quantco/pixi-pack/blob/v0.7.11/README.md)说明从锁文件下载
目标架构包，不要求本机已安装该环境；目标平台解包仍需同平台主机。

工具下载与校验（均为官方 GitHub release 资产）：

```text
              sha256 7aa3ec39aecceff9062fa2ed4d42cbaa0bdc25ddea727d048e061cf188d434f6
              与 release 附带的 .sha256 文件一致；gzip -t 通过；pixi --version = 0.81.0

              sha256 4f2e6b70433c846974b9bd1356456335028afbe23f1fdf856ffa022ed691fc22
              与第一轮记录一致；pixi-pack --version = 0.7.11
```

最小项目（与第一轮相同）：

```toml
[workspace]
name = "rospm-p0-robostack"
channels = ["https://conda.anaconda.org/robostack-humble", "https://conda.anaconda.org/conda-forge"]
```

在 x86_64 主机上执行：

```bash

                                             # 7.4 s，"Downloading 34 packages"，产物 76.81 MiB
```

产物检查：

- `environment.tar` 80544256 字节，sha256
  `b0e328f4368620fef7b79d8571415eb2c54d3f44bfe070dd8629e289f1dd4a15`。
- 归档内 `pixi-pack.json` 为 `{"version":"1","pixi-pack-version":"0.7.11","platform":"linux-aarch64"}`，
  另含 `environment.yml`、`channel/linux-aarch64`（32 个 `.conda`）与 `channel/noarch`（4 个 `.conda`），共 34 个包。
- 用脚本把 `pixi.lock` 中全部 34 条 `conda:` 记录的 sha256 与归档内同名文件逐一比对：
  34 个全部匹配，没有缺失，也没有多余文件。
- 其中 `ros-humble-ros-workspace-1.0.2-np2py312h61f2ce4_18.conda` 35551 字节，sha256
  `08a5c8bd2139dd86b3ee85e6384b82b6b0b291fd9e2667c2be919422ecbde926`，
  与 anaconda.org 元数据一致。
- `pixi.lock` sha256 `0615604d81af769e8eb3192be3d246ef7fa46e65ebf1c553e57a2b51085c2e99`。

结论：x86 主机为 linux-aarch64 生成锁文件并打包是可行的，且包内容可用锁文件哈希独立复核
（P6 的 bundle 校验可直接复用这个思路）。**ARM 主机上的 `pixi-unpack` 与运行尚未实测**，
需在 P3/P5 用真实 aarch64 机器或 GitHub ARM runner 补做；不可把 x86 打包成功等同于 ARM 运行成功。

## 4. RoboStack rosdep 源与 skip_keys（2026-09-25 补齐 conda-forge 构建实测）

实际源链：

- [conda-forge rosdep 配方](https://github.com/conda-forge/rosdep-feedstock/blob/main/recipe/meta.yaml)
  为 0.26.0、build 1，应用 `add-robostack.patch`、`810.patch`、`no-sudo.patch`。
- [add-robostack.patch](https://github.com/conda-forge/rosdep-feedstock/blob/main/recipe/add-robostack.patch)
  把默认源列表改为
  `https://raw.githubusercontent.com/RoboStack/rosdistro/master/rosdep/sources.list.d/20-default.list`。
- 该列表优先加载 `https://raw.githubusercontent.com/RoboStack/ros-noetic/master/conda.yaml`，
  再加载标准 base/python/ruby YAML。路径中的 noetic 不能被误解为只可解析 Noetic 系统依赖。
- `ROSDEP_SOURCE_PATH` 可隔离 sources 目录，`ROS_HOME` 可隔离缓存；指定
  `--os=conda:linux`。不要把 native 和 Pixi 的全局源列表相互覆盖。
- `ros-humble/main/robostack.yaml` 是 vinca 构建映射，使用 `robostack:` 键，
  不是上述 `conda:` rosdep 源的直接替代品。

### 4.1 上游 master（第一轮）

使用上游 rosdep master 源码（报告版本 0.27.0）、独立缓存，`update --rosdistro humble` 成功。
系统键映射正常，但 `rclcpp` 在 `--os=conda:linux` 下报
`No definition of [rclcpp] for OS [conda]`；上游 conda 后端仅支持映射，检测/安装抛出
`NotImplementedError`。

### 4.2 conda-forge 0.26.0 build 1（第二轮）

用 pixi 在独立环境安装 `conda-forge::rosdep==0.26.0`，锁定到
`noarch/rosdep-0.26.0-pyhd8ed1ab_1.conda`（sha256
`73eebdcdebc4f78053dcfcd7366a3a07ad7e6c259125c1f22e411816a1fff89f`，与第一轮记录一致）。
`rosdep2.sources_list.DEFAULT_SOURCES_LIST_URL` 实测已是 RoboStack 列表，证明补丁生效。
以独立 `ROSDEP_SOURCE_PATH` / `ROS_HOME` 执行 `rosdep update --rosdistro humble` 成功
（首次因 raw.githubusercontent.com 读超时失败，重试后通过；这是网络问题）。

`rosdep resolve <key> --rosdistro humble` 对照：

| rosdep 键 | `--os=ubuntu:jammy` | `--os=conda:linux` |
|---|---|---|
| boost | libboost-all-dev | libboost-devel libboost-python-devel |
| cmake | cmake | cmake |
| python3-numpy | python3-numpy | numpy |
| libopencv-dev | libopencv-dev | py-opencv libopencv libopengl-devel libgl-devel |
| rclcpp | ros-humble-rclcpp | **ros-humble-rclcpp** |
| ros_workspace | ros-humble-ros-workspace | ros-humble-ros-workspace |
| ament_cmake | ros-humble-ament-cmake | ros-humble-ament-cmake |

系统键与第一轮上游 master 结果完全一致；ROS 包键在补丁版下能映射为
`ros-humble-*` conda 包名（`robostack-humble` 频道确有 `ros-humble-rclcpp` 16.0.19，
linux-64 / linux-aarch64 等平台均有构建）。

`skip_keys` 语义复验：对含 `ament_cmake / rclcpp / boost / libopencv-dev / python3-numpy`
的 `package.xml` 执行 `rosdep keys --skip-keys libopencv-dev`，输出仍包含 `libopencv-dev`；
`check` / `install --simulate` 则正确排除。与第一轮结论一致。

**新发现：补丁版 rosdep 的 conda 检测依赖 micromamba 1.x 的 JSON 格式。**
`rosdep check` / `install` 在 `--os=conda:linux` 下要求 PATH 上有 micromamba / mamba / conda。
- 没有任何一个时：`Bad installer [conda]: None of micromamba, mamba, conda was found.`
- micromamba **2.9.0**：`Bad installer [conda]: string indices must be integers, not 'str'`。
  原因是 `rosdep2/platforms/conda.py::conda_detect` 把 `micromamba list --json` 当作列表遍历，
  而 micromamba 2.x 返回 `{"log_history": [...], "packages": [...]}`。
- micromamba **1.5.12**（`micromamba<2`）：`check` 正确列出未满足的 conda 包
  `ros-humble-rclcpp libboost-devel libboost-python-devel numpy ros-humble-ament-cmake`；
  `install --simulate` 输出 `micromamba install ros-humble-rclcpp libboost-devel libboost-python-devel numpy ros-humble-ament-cmake`（exit 0）。

对 P3 的约束：

- `resolve` / `keys` 不依赖 micromamba，可以放心用于生成 `pixi.toml` 的依赖列表；
  这是 rospm 真正需要的路径，安装交给 pixi。
- 如果 P3 需要复用 rosdep 的 `check`，必须固定 micromamba 1.x，或者自行读取
  `pixi list --json` 求差，不要依赖 rosdep 的 conda 检测。
- 清单的 `skip_keys` 共用原始 rosdep 键，Pixi 流程须在解析前自行过滤；
  不能拿 apt 包名过滤 conda 解析结果。包名相同不代表所有键跨提供者存在。
